1. 先读本文，分清板上程序、最新候选、离线模型与实车证据。
2. 看根目录 README、`docs/WIRING_AND_COMMANDS.md`、`docs/LIDAR_LINK.md`；旧版本段落以本文更新为准。
3. 从 `src/nav_main.c` → `src/nav/nav_app.c` → `nav_route.c` / `nav_map.c` 理解整车执行链。

5. 从 `src/nav/nav_arm.c` → `arm/project/APP/arm_task.c` 理解机械臂集成；不要另造一套高度零点。
6. 再看 `lidar/firmware/APP/Src/app.c`、`features.c`、`BSP/Src/vehicle_tx_queue.c`，核对两板协议。

不要根据目录名推断新旧。主控候选在本机曾存放于 `matlab/studio_scene_20261114`；这里发布为仓库根目录工程，依然是实机运行的C源码，不是MATLAB替代控制器。

## 3. 任务目标与不可随意改变的约束

- 服务2027工创赛：二维码停车、两批各3块供料、粗加工放置/取回、暂存区第一批平放与第二批码垛，然后直接回启停区1。
- 粗加工坚持 **1→2→3放，1→2→3取**，不能为了时间擅自改成逆序取回。
- 原料手动供料阶段相邻开始抓取至少间隔5s；二维码阶段可先停车5s模拟。真实视觉未接入不能宣称已识别颜色/二维码。
- 下位机负责路径规划；主机发送障碍位置/任务/参数，不以PC预规划轨迹冒充MCU自主避障。
- 用户希望初段到二维码区时勘测定图，后续避免反复停车重规划；雷达后续应主要提供外部定位约束，真实新危险仍可停车。
- 两柱可能都在黄色区，或只封一条/零条通道；不能强制必须识别出两条禁行道路。
- 历史时间目标：完整任务约150s、快速导航约60s。目前未证明达到；不能用纯导航时间代替含24次取放的总时间。
- 用户要求运行全程保留日志，正常时不需要人工一直读日志；出错或结束后分析。实车发车仍需事先确认。

## 4. 具体技术栈

### 4.1 主控固件

| 层 | 技术/实现 |
|---|---|
| 芯片 | STM32F407VET6，Cortex-M4F，HSE25MHz、SYSCLK168MHz |
| 软件形态 | C11、裸机主循环/中断，无RTOS；ST HAL/CMSIS与少量寄存器直接操作 |
| 编译 | GNU Arm GCC 13.3.1（STM32 GNU工具链），Python构建脚本 |
| 浮点/优化 | `-mcpu=cortex-m4 -mthumb -mfpu=fpv4-sp-d16 -mfloat-abi=hard -O2`；不启用fast-math |
| 诊断 | `-Wall -Wextra -Werror`、链接map、反汇编、函数栈用量；硬件DWT新版本最坏耗时仍待测 |
| 控制 | F6连续速度命令；上层轨迹/位置反馈→车体系速度→麦轮逆解→轮速约束 |
| 控制律 | cascade、ADRC/ESO、LQR、QP/MPC候选；本批场景验证使用cascade，不能宣称其余算法全图已通过 |
| 轨迹 | 加减速与航向同步轨迹，连续导引点，到作业站停车；原料接近段单独约束 |
| 定位 | 编码器+WT901航向的base；另有fused与独立雷达XY修正入口，三者不能混为一谈 |
| 部署算法 | `src/nav/generated/`、`src/nav/qp/` 是实机依赖的生成C，必须保留；不需要在车上运行MATLAB |
| 存储 | 主控Flash sector7保存机械臂标定；运行障碍记忆在RAM |

代码区限制384KiB，为标定预留空间；当前FLASH占206836B（52.60%）。主控RAM链接占118712/131072B（90.57%，含8KiB栈预留）。没有新的实板栈水位或最坏耗时测量，不能据主机仿真速度推断F407实时性。

### 4.2 独立雷达板

- 同为F407VET6/25MHz/168MHz，C11裸机，CMake3.20+、Ninja、GNU Arm GCC。
- LD19原始包47字节、每包12点、CRC8；分圈与微秒时间戳，DMA/环形缓冲处理。
- `features.c` 负责滤波、簇/线段、跨圈跟踪；`motion_history.c` 利用主控位姿提示去畸变。
- `pose_match.c` / `shadow_localizer.c` 是局部候选，不能视为已接入主控的全局真值。
- `vehicle_tx_queue.c` 为板间完整帧优先队列；时钟/配置回包不能被大批观测长期阻塞。
- TIM2微秒时基；DMA缓冲必须在DMA可访问SRAM，不能随意挪入CCM。
- W25Q128、24C02有板级接口/诊断，不代表已有永久建图或完整SLAM。
- 本次重建FLASH44868B、RAM81480B、CCM未使用；工具链与镜像哈希见build.json。

## 6. 硬件接线与通信

所有UART为3.3V TTL、8N1，TX/RX交叉、GND共地。电机/舵机不能由下载器3.3V供电；独立供电输出不要并联。

| 功能 | 主控F407 | 对端 |
|---|---|---|
| PC调试，115200 | USART1 PA9 TX / PA10 RX | DAP串口RX / TX；本机通常COM13 |
| 五Emm，115200 | UART4 PA0 TX / PA1 RX | 驱动器RX / TX，含升降ID5 |
| WT901CTTL，默认115200 | USART3 PD8 TX / PD9 RX | WT901 RX / TX；当前初始化以源码为准 |
| 雷达双板，230400 | USART2 PA2 TX / PA3 RX | 雷达板PB11 RX / PB10 TX |
| 视觉，默认115200 | UART5 PC12 TX / PD2 RX | OpenMV RX / TX |
| 舵机1/2/3/4，50Hz | TIM3 PC6 / PC7 / PC8 / PC9 | 夹爪/云台/料盘/摄像头 |
| SWD | PA13 / PA14 / GND，可选NRST | SWDIO / SWCLK / GND |

| 雷达板功能 | 引脚/参数 |
|---|---|
| LD19 TX输入 | PA3 USART2 RX，230400；沿用已核对线束，不能按颜色猜引线 |
| PC调试 | PA9 TX / PA10 RX，460800；本机通常COM3 |
| 主控链路 | PB10 TX→主控PA3；主控PA2→PB11 RX；230400 |
| W25Q128 | PC13 CS，SPI1 PA5 SCK/PA6 MISO/PA7 MOSI；PC13不能当LED |
| 24C02 | PB6 SCL/PB7 SDA，已有3.3V上拉，7位地址0x50 |

两块板的PA3是不同物理节点。行驶时雷达板无需连接电脑；主控接收它的数据并记录诊断。串口号会随USB枚举变化，下载前核对实际板身份，不能只看COM数字。

四轮逻辑顺序FL/FR/RL/RR对应Emm地址 **4/1/3/2**，编码器符号 **+/-/+/-**。不要按地址排序重排轮数组。升降为ID5，同一TX/RX总线。

## 7. 坐标系和标定

### 地图M、导航N、车体B、雷达L

- 地图2400×2400mm，M原点左下，X向右、Y向上。
- N原点为启停区1中心且初始车头朝图左：`Mx=2250-Nx`、`My=2250-Ny`（mm）。区2中心N=(0,2100)。
- B：+X向车头，+Y向车左，−Y是车右/机械臂安装侧。运行中B随航向转动，不能把车体修正量直接累加到地图。
- 雷达原始270°朝前、180°朝右；当前外参B中X+120mm、Y0，主控设置mirror on和yaw90000mdeg。
- 当前有效视场 **前150°**，雷达原始195°..345°；旧180°半周及后方88°..92°窗口已停用，不能据旧文档认为后方可见。
- 内部单位多为米/弧度；文本通常毫米/毫度，雷达时间微秒、主控时间毫秒，必须在边界显式换算。

四块黄色区仅地面色块，没有高度；雷达不能直接识别黄区，必须保留固定地图约束。车体收拢约300×300mm；扫描平面离地高度和车架遮挡尚未完整测量。

### 已测工位偏置与机构

原料区、粗加工区、左侧暂存区的车体修正原始记录分别为(+20,+44)、(+28,+18)、(+14,+60)mm，已按当时各工位朝向变换到 `nav_map.c` 的N偏置；不要再重复叠加一次。粗加工和暂存均为三个点的中间点标定，相邻中心距150mm。

夹爪闭1560/开1850μs；云台内1000/外2130μs；料盘550/1450/2350μs。升降历史安全高度LOCAL−2306，仅在正确实体参考下有效。Flash高度记录不是驱动器跨断电物理绝对位置。

主控Flash sector7为 `0x08060000..0x0807FFFF`，禁止随意全片擦除。`recover zero`和`recover clearance`是对已确认实体姿态的声明，不是自动寻找零点，也不会把机构实际移动到那里。标定数据不在本次公开仓库发布。

## 8. 双板协议与定位关系

帧：`AA 55 CMD SEQ LEN PAYLOAD XOR`，LEN≤250，多字节小端，float32；XOR涵盖此前整帧。保持原风格，不额外要求心跳/启动握手。

| 命令 | 方向 | 作用 |
|---|---|---|
| 0x66 / 0xE6 | 主控↔雷达 | nonce/ms及雷达接收/回复us的时钟采样 |
| 0x68 / 0xE8 | 主控↔雷达 | 会话与感知流配置，重置过期运动上下文 |
| 0x65 | 主控→雷达 | 同步到雷达时钟域的运动提示，供去畸变，不是独立测量 |
| 0x73 | 雷达→主控 | 同圈跟踪批次，11字节头＋32字节记录，单批≤7条、整圈≤32条 |
| 0x75 | 雷达→主控 | 视场元信息，本版前150° |
| 0x76 | 雷达→主控 | 同扫描匹配的线段端点/半厚度；缺失不能当作自由空间 |

批次必须同圈、同时间、完整且顺序正确才提交。近未来扫描可等历史追上，不能当永久坏帧；真正过期仍拒绝。时钟RTT/突跳及scan年龄保护保持，不能为消除报错而关掉同步检查。

`mode fused`与`lidar fusion on`不是同一个开关；当前默认STUDIO_FUSED=0，本批仍为base。现有雷达XY入口要求足够稳定地标、至少3个唯一匹配及足够空间跨度，限制创新和修正速率；它不是完整SLAM。主控位姿提示派生出的shadow不能重新当独立外部真值闭环融合。

## 9. 二维码板：接手者必须处理的实体回波问题

**用户最新明确要求：二维码板能被雷达扫到，不能因此反复停车、错误封路或影响扫码接近。此项当前只交接，不改代码；不得标成已实现/已验证。**

### 9.1 事实与未知量

- 原料盘和二维码板在比赛开始时的位置并非一个精确固定值，有地图允许区间；启动之后相对场地静止。
- 原料盘沿地图上边的中心横向范围1100..1300mm；右侧二维码站的纵向名义区间也应结合赛事地图/发布稿1100..1300mm定位。二维码名义停车点为N(125,1050)mm，不能据此认定板实体就在该点。
- 板是平面实体，可能有支架/底座，雷达能否扫到取决于扫描高度。板面尺寸、实际厚度、支架包络和安装扫描高度尚未完整测量。
- 雷达看到的是几何回波，不会因此读取二维码内容；真正扫码仍属于摄像头/OpenMV。

### 9.2 应遵守的设计边界

1. 不按“在二维码附近”整块删除所有点；真实柱子/观众侵入/板向通道突出仍需要防撞。
2. 长板尽量保持线段或窄面包络。**线段中心在场外，不代表端点也在场外；线段中心在已知设施内，也不允许把伸向通道的端点屏蔽。**
3. 若以后增加设施关联，使用允许位置区间、稳定跨帧几何、方向和范围证据；不能把未知板位置硬编码成绝对地标，不能仅凭邻近站名就免检。
4. 将“可用于定位的静态设施”“阻挡车体的实体”“尚不确定的弱回波”分开：设施可以参与估计，但其真实占据仍阻止碰撞；弱回波不能立刻永久封路。
5. 地图冻结后不要把二维码板抖动/分簇/ID切换解释成新的两根黑柱；也不能无条件吞掉贴在板边的真柱。
6. 接近板/支架时必须检查300mm旋转车身和制动路径；需要扫码停点补偿时直接修正作业目标，不能反复重建N原点。
7. 二维码板若用于外部定位，先估计其启动后的固定位置及不确定度；视觉/雷达/地图的参考系变化应走明确变换，不能把导航目标、测量地标和主控预测混为同一真值。

### 9.3 必须补齐的仿真/实测矩阵

| 场景 | 验收要求 |
|---|---|
| 板位于允许区间两端/中点 | 不强制卡在单一坐标；扫码站能规划接近 |
| 板面正对/倾斜、支架突出 | 以端点/实体包络判断，有碰撞风险就停，不误当圆柱封整条路 |
| 板中心在场外、边缘伸入场内 | 不能按中心场外过滤丢掉侵入端点 |
| 板前/板边另放一根50mm柱 | 设施关联不能屏蔽柱子 |
| 板分成多簇、跟踪ID变化、短暂遮挡 | 不膨胀成大量永久障碍，不因丢一帧清空 |
| 二维码附近场外观众/移动物体 | 完全无关场外回波不堵路，侵入车体路径仍保护 |
| 扫码停稳/360°观察及离站 | 不因板回波反复触发重规划；不能在盲侧假定无障碍 |
| 时间偏差/坏包/缺段/重启 | 保护与诊断可重复，不静默使用旧会话 |

现有39条场景断言已包含“长线段中心在原料设施核心也不继承圆簇屏蔽”，但这不是二维码板完整测试。前一批107例未完整渲染二维码板、场外围观者或三维自遮挡。必须新增上述用例并保留失败，不能直接复用“107通过”给二维码板背书。

## 10. v2.7.38 的实际改动

1. 原料设施核心弱回波先关联固定设施，再做近回波分层；固定实体的碰撞约束未取消，邻近真实柱仍保护。
2. 障碍记忆需6个不同扫描、≥450ms稳定证据，间断>500ms重启候选；同ID大离群不另建圆，换ID可空间关联，不再永久求并膨胀。
3. 纯导航二维码观察后停稳1s冻结确认地图，后续只重新规划一次，不重置原点；冻结后新危险停车，不反复自动绕行。
4. 勘测前右侧纵道先朝向行驶，减少前150°视场的侧移盲区。
5. 冻结且已覆盖的障碍沿真实未来路径检查，避免把当前速度直线外推到转弯后的障碍上；未知物和当前车身重叠仍保护。
6. 通行路口与工位标定坐标分开。上中路口直行N(1050,200)mm，转向时先进入N(1050,275)mm转向位置；仍是九路口图，不加细网格。
7. 原料区原有最后250mm接近约束跨导引点生效；末端未静止时保留反馈阻尼。全局轮速上限和保护阈值没有为隐藏误差而调低/放宽。

**范围限制：自动二维码冻结当前只接入纯导航；分段标定、手动机械臂、完整任务没有全部接入新冻结状态机。**

## 11. 软件验证结果及不能声称的结论

- 主控31组本机C回归全部通过，其中场景断言39条。
- MATLAB最终107例：6例旧版参考，候选96例完整导航、4例预期保护停车、1例强打滑失败。
- 66种两柱通道组合：65种完成；2+5封死启停区1的两条出口，按九路口图无路，安全停止。
- 3例逐束450束/100ms模型运行实际雷达提取/跟踪/发送与实际主控解析；另有通信延迟、扫描丢失、时钟抖动、满批次、噪声、IMU偏置、负载、摩擦变化等回归。
- 100RPM上限纯导航约116.7～156.0s，中位128.6s。5个匹配种子组合，200RPM约122.5～132.6s。**不包含完整取放动作，不代表150s整场目标已实现。**
- 严重单轮打滑2s反例：最终误差约79.4mm，并压黄区/越界/接触设施，尽管软件可报告DONE。这是明确失败，不能忽略。
- MATLAB模型重量/惯量/摩擦与响应常数尚未实车辨识；不完整模拟反射率、多径、线缆和三维遮挡。MEX规划不消耗虚拟运动时间，不能替代F407最坏耗时测量。
- 记忆障碍坐标依赖里程计，冻结不等于绝对准确。前150°之外的新障碍和从未看见的障碍不能保证检出。
- 用户此前要求忽略突然出生的极近回波；该策略同样可能忽略满足条件的真物体，应在竞赛工况内明确验证，而不能宣称完美近障检测。

完整原始数据、MAT文件、日志和仿真脚本仅本机保留，不随此仓库发布。公开文档给出总结和限制，不上传原始测试数据。

## 12. 编译与镜像核对

安装Python3.9+、GNU Arm GCC；雷达再安装CMake3.20+与Ninja。工具加PATH或设置环境变量：CHASSIS_GCC、ARM_GCC、CMAKE、NINJA，值为对应可执行文件。仓库根目录执行：

```powershell
python scripts/build_nav.py
python lidar/tools/build.py
```

都是只编译入口，不开串口、不接下载器。输出 `build/nav1k/` 与 `lidar/build/Release/`。发布镜像在两个 `firmware/current/`，build.json含版本、源文件相对路径哈希和BIN哈希。

BIN基址 `0x08000000`，HEX自带地址。不要把ELF/DWARF、完整Flash备份、标定sector7或本机路径配置提交公开仓库。编译器/路径变化可能改变调试符号，但本次发布重建的主控BIN已与候选一致。

## 13. 常用命令与危险的误用

命令带换行；具体语法以当前C解析为准。这里不是可直接整段执行的发车脚本。

| 类别 | 命令/说明 |
|---|---|
| 只读 | `status`、`odom`、`perf`、`imu`、`arm status`、`arm points`、`lidar status` |
| 现场快照 | `lidar tracks`、`lidar memory list`、`lidar hazard`及live/near/memory、`lidar plan`及live/memory |
| 停止 | `stop`或`!`，随后核对四轮停止/失能应答及实体停稳 |
| 控制/定位 | `algorithm cascade`、`mode base` / `mode fused`、`control xy`；切换不是定位真值恢复 |
| 当前外参 | `lidar mirror on`、`lidar mount 120 0 90000`、`lidar self 145 145 145 145` |
| 感知/记忆 | `lidar obstacle on`、`lidar memory on`；`lidar memory survey`恢复建图，`lidar memory freeze`冻结，不是自动补扫 |
| 规划 | `map lidar`、`route avoid on`、`route qr on`、`route sensorplan 50`只规划；`route preflight`前检；`route start`会运动 |
| 运动 | `run forward 100 5`等、`pose ...`、`turn ...`都会运动；turn使用导航绝对航向 |
| 升降参考 | `arm recover zero` / `arm recover clearance`仅实体位置确认后使用 |
| 机械臂 | `arm motion fast`、`arm grab 1`、`arm rough 1`、`arm unrough 1`、`arm stack 1`都会动作 |
| 相机高度 | `arm point view` / `arm point qr`记录，`arm height view` / `arm height qr`移动到已标定高度 |
| 舵机 | `arm servo 2 2130`外、`arm servo 2 1000`内；PC9为servo4，相机PWM姿态仍需测量 |
| 保存 | `arm save`保存高度，不保证驱动器断电后原坐标仍成立 |

`origin`/`frame restore`是实体起点坐标声明，不是每次报错都调用的清错按钮。`clear`也不能修复丢失的实体基准。`arm measure on`会撤去升降力矩，需要实体支撑。相机俯视/二维码高度没有有效标定就不能猜值运行。

## 15. 接下来按什么顺序做

1. 先检查二维码板第9节的几何与失败矩阵，测量扫描平面、板/支架实际包络，不直接整圈试错。
2. 补全离线板回波、场外人、近物出生、遮挡/乱序/重启、时间同步稳定性测试；失败必须保留。
3. 实板只读/静态核对双板版本、外参、时间、扫描、五电机总线、标定；再测F407执行耗时和栈余量。
4. 发车前确认车位、车头、升降实体高度和场地；不能因为上次说过“安全高度”就默认本次仍成立。
5. 低速验证二维码观察和定图，导航通过后再合入完整机械臂任务的冻结/解冻状态。每次任务只声明一次实体起点，不在途中重建原点。
6. 严重滑移先改善独立观测的可观测性/关联，明确退化和拒绝机制，再测定位；不是调大增益、缩小协方差或复制预测位姿就能解决。
7. 最后才优化动作叠加和总时间：保持123放/123取，车身与伸臂包络真实可证，导航和作业耗时分别统计。
